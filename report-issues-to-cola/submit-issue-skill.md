# Submit Issue

当用户反馈问题或提出需求，并要求提 Issue 时，按以下流程执行。

## 第一步：判断类别

根据用户描述判断 Issue 类型：

| 类型 | 信号 |
|------|------|
| Bug | "不对"、"做错了"、"报错"、"和预期不符"、异常行为描述 |
| Feature | "希望有"、"能不能加"、"需要一个"、新功能描述 |
| Perf | "太慢"、"卡顿"、"加载时间长"、性能相关描述 |

如果判断不准，主动向用户确认。

## 第二步：收集信息

从当前对话上下文中提取：

**Bug**：
- 复现步骤（用户做了什么操作、说了什么）
- API 请求与响应日志（接口、请求体、状态码、响应体）
- 补充信息：发生环境、出现频率、根因判断

**Feature**：
- 需求描述与场景（解决什么问题、什么场景下使用）
- 期望行为（操作后应该看到什么结果）

**Perf**：
- 问题描述（什么操作慢、卡顿或资源异常）
- 当前数据（可获取的性能指标，如响应时间）
- 目标（期望优化到什么水平）
- 瓶颈分析
- 优化方向

信息不足时追问用户，不要编造。

## 第三步：确定 Label

根据问题涉及的层级打 Label：

| Label | 层级 | 职责 |
|-------|------|------|
| App | 业务层 | 用户交互、UI、产品体验 |
| Agent | Agent 层 | 意图理解、任务执行、上下文管理 |
| Infra | Infra 层 | 工具开发、底层基建、稳定性 |

跨层问题打多个 Label。

## 第四步：确定优先级

根据影响范围和严重程度判断：

| 优先级 | 含义 |
|--------|------|
| P0 | 阻断性问题，核心功能不可用（无法启动、数据丢失、安全漏洞） |
| P1 | 严重影响体验，但有 workaround |
| P2 | 一般问题，不影响核心流程 |
| P3 | 改进建议，低优先级 |

## 第五步：提交 Issue

标题格式：`[Bug] xxx`、`[Feature] xxx` 或 `[Perf] xxx`

执行命令：

```bash
gh issue create \
  --repo marswaveai/cola-internal-feedback \
  --title "[类别] 标题" \
  --label "层级Label,优先级Label" \
  --body "Issue 正文"
```

如果 `gh` 未安装或未登录，引导用户执行：
1. 安装：`brew install gh`
2. 登录：`gh auth login`
